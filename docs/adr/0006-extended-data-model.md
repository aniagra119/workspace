# 0006: Extended Data Model — Versioning, Multi-Backend, Unstructured Data, Tracker Registry, Computed Views

**Date:** 2026-05-20
**Status:** Accepted

## Context

The current data model assumes a single structured backend (Google Sheets) with flat tabular rows. Five architectural requirements force this to expand:

1. **Schema versioning** — `_MANAS_CONFIG` and `_MANAS_SCHEMA` evolve over time. There is no mechanism to detect when a schema change breaks a downstream node or rule.
2. **Multi-backend support** — not all backends support the same operations. `DatabaseClient.create_table()` is trivial in Sheets but requires a migration in PostgreSQL. The Protocol must expose capability declarations so nodes degrade gracefully.
3. **Unstructured data** — voice transcripts, raw notes, image descriptions, and long-form reflections cannot be stored as flat row values. They require a separate blob/vector store for semantic retrieval.
4. **AI-driven tracker lifecycle** — the system must be able to CREATE a tracker (schema + rule set), ACTIVATE it, CONSUME it (read and surface insights), and DEPRECATE it without manual schema edits.
5. **Computed/derived views** — read-only aggregated views (e.g. monthly spend summary, rolling 7-day mood average) should be generated by the AI and stored as native computed tabs, not as live query results that burn API quota on every read.

## Decisions

### A. Schema Versioning

Every system-owned tab (`_MANAS_CONFIG`, `_MANAS_SCHEMA`, `_MANAS_TRACKERS`) carries a `schema_version` column in its first row header group. The `SchemaInspectorNode` reads this version on boot and compares it against the `EXPECTED_SCHEMA_VERSION` constant in the codebase.

If a mismatch is detected, the node writes a `trajectory` entry flagging the drift and triggers a `SchemaMigrationNode` (non-blocking, queued separately) rather than crashing the graph. The graph continues with the last-known cached schema.

Node contracts, client Protocols, and `AgentState` fields are versioned independently via the Developer Palette branch tag (`python/feature-langgraph@v2.x.x`). Breaking changes to a Protocol method signature require a major version bump.

### B. Database Capability Map

Each `DatabaseClient` implementation declares a static `CAPABILITIES` map. The `SchemaInspectorNode` reads this at boot and stores it in `AgentState.db_capabilities`. `DatabaseWriterNode` checks this before issuing structural operations.

```python
@dataclass(frozen=True)
class DatabaseCapabilities:
    supports_create_table: bool
    supports_add_column: bool
    supports_computed_fields: bool    # Notion formulas, Airtable rollups, SQL views
    supports_transactions: bool
    supports_full_text_search: bool
    max_rows_per_write: int           # Sheets: 1000, PostgreSQL: unbounded
    backend_type: Literal["spreadsheet", "relational", "document", "key_value"]
```

Supported backends and their capability profiles:

| Backend | Type | create_table | add_column | computed_fields | transactions |
|:---|:---|:---:|:---:|:---:|:---:|
| Google Sheets | spreadsheet | ✅ | ✅ | ✅ (formula cells) | ❌ |
| Notion | document | ✅ | ✅ | ✅ (rollups, formulas) | ❌ |
| Airtable | spreadsheet | ✅ | ✅ | ✅ (rollups) | ❌ |
| PostgreSQL | relational | ✅ | ✅ | ✅ (SQL views) | ✅ |
| SQLite (local) | relational | ✅ | ✅ | ✅ | ✅ |
| Redis | key_value | ❌ | ❌ | ❌ | ❌ |

Redis is never a primary `DatabaseClient` — it is exclusively the hot-state and write-debounce layer.

### C. Unstructured Data — VectorClient Protocol

A third injectable Protocol handles unstructured data:

```python
class VectorClient(Protocol):
    """Store and retrieve unstructured data via semantic embedding search."""
    async def upsert(self, doc_id: str, content: str, metadata: dict) -> None: ...
    async def search(self, query: str, top_k: int, filters: dict | None) -> list[dict]: ...
    async def delete(self, doc_id: str) -> None: ...
```

When the `SemanticGatewayNode` determines input is unstructured (long-form note, voice transcript, image description), it sets `intent.store_as_vector = True`. The `DatabaseWriterNode` routes to the `VectorClient` instead of the tabular `DatabaseClient`.

The `_MANAS_SCHEMA` tab gains two new column fields to support this:
- `storage_type: enum` — `tabular` | `vector` | `both` (extract key fields to table + store raw in vector store)
- `vector_namespace: str` — which namespace/collection in the vector DB this persona maps to

Supported vector backends (all implement `VectorClient`):
- **Upstash Vector** (serverless, zero cold start — matches the Lambda deployment model)
- **Pinecone** (managed, higher throughput)
- **pgvector** (if PostgreSQL is the primary backend — single DB for both structured and vector data)
- **Chroma** (local dev/testing)

### D. Tracker Registry (`_MANAS_TRACKERS`)

A tracker is a named, versioned unit that combines:
- A set of columns in `_MANAS_SCHEMA` (what to measure)
- A set of rules in `_MANAS_CONFIG` (when to prompt for data, when to surface insights)
- An optional computed view (aggregation formula or SQL view)

A new system tab `_MANAS_TRACKERS` manages tracker lifecycle:

| Column | Type | Description |
|:---|:---|:---|
| `tracker_id` | `str` | Unique slug (e.g. `sleep_quality`) |
| `persona_id` | `str` | Parent persona |
| `display_name` | `str` | Human-readable name |
| `status` | `enum` | `proposed` \| `active` \| `paused` \| `deprecated` |
| `proposed_by` | `enum` | `ai` \| `user` |
| `schema_columns` | `json` | Column definitions to add to `_MANAS_SCHEMA` |
| `rules` | `json` | Rule definitions to add to `_MANAS_CONFIG` |
| `computed_view_id` | `str` | FK to `_MANAS_VIEWS` if a computed view exists |
| `version` | `str` | Semantic version of this tracker definition |
| `created_at` | `datetime` | |
| `deprecated_at` | `datetime` | Nullable |

The AI proposes a tracker by writing a row with `status = proposed`. The user approves via a Discord Component button, which flips `status = active` and triggers:
1. `DatabaseWriterNode` adds columns to `_MANAS_SCHEMA`
2. `ConfigManagerNode` writes rules to `_MANAS_CONFIG`
3. `SchemaInspectorNode` cache is invalidated

Deprecating a tracker sets `status = deprecated` and removes its rules from `_MANAS_CONFIG` but does **not** delete historical data columns.

### E. Computed Views (`_MANAS_VIEWS`)

A computed view is a read-only tab generated by the AI containing aggregated data. Unlike a live query, it is a **materialized snapshot** refreshed on a configurable schedule by the Manthan Engine.

| Column | Type | Description |
|:---|:---|:---|
| `view_id` | `str` | Unique slug (e.g. `monthly_spend_summary`) |
| `persona_id` | `str` | Source persona |
| `display_name` | `str` | Tab name in the spreadsheet |
| `view_type` | `enum` | `formula` \| `sql_view` \| `materialized` |
| `definition` | `json` | Backend-specific view definition (formula range, SQL SELECT, aggregation spec) |
| `refresh_schedule` | `str` | Cron expression for Manthan Engine refresh |
| `last_refreshed_at` | `datetime` | |
| `is_protected` | `bool` | If true, `DatabaseWriterNode` refuses to write to this tab |

The `DatabaseClient` Protocol gains one new optional method:

```python
async def create_view(self, view_ref: str, definition: dict, capabilities: DatabaseCapabilities) -> None:
    """Create a computed/derived view. Backend-specific implementation."""
    ...
```

For Google Sheets, this creates a new tab populated with QUERY() or SUMIF() formulas. For PostgreSQL, it executes `CREATE VIEW`. For Notion, it creates a linked database view with filters and rollups. If the backend does not support computed fields (`capabilities.supports_computed_fields = False`), the Manthan Engine falls back to materializing the view by running the aggregation query and writing the results as static rows.

## Consequences

- `AgentState` gains `db_capabilities: DatabaseCapabilities` and `vector_client: VectorClient | None`.
- `DatabaseWriterNode` must check `capabilities` before structural operations and route vector-flagged inputs to `VectorClient`.
- `_MANAS_SCHEMA` gains `storage_type` and `vector_namespace` columns — a schema migration is needed for existing installations.
- The Developer Palette `python/feature-langgraph` branch gains a `python/feature-vector` branch for the `VectorClient` Protocol and concrete implementations.
- The Manthan Engine becomes responsible for view refresh scheduling, adding a recurring job responsibility beyond its current ad-hoc analysis role.
